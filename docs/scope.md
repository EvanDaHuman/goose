# Execution scope

Goose accepts engineering objectives across software domains. Execution depends on a reproducible environment and an approved contract. Inspection alone is never represented as completed work.

## General repository engineering

Live Naïve assessment creates source/target build commands, preserved behaviors, new requirement checks, required files and limitations. Commands use bounded argv arrays. Native tool names include Python, Node, Cargo/Rust, Go, C++, CMake, CTest and Make when installed. Compiled executables inside the job can run. Dependencies must already be available because candidate execution has no network.

Source checks run on two fresh copies before quotation. After approval, the baseline runs again and its hashes are frozen outside the implementation workspace. Naïve creates the candidate. Separate tools build and check it, enforce repair limits and bind delivery to the exact verified files.

This covers algorithm migration, bug fixes, CLI features and build/configuration changes when substantive checks exist. It does not mean every repository, framework or integration is supported. Nondeterministic outputs require suitable normalization. Native execution currently requires macOS; other native hosts fail explicitly.

## Service and data executors

The inherited pipeline supports targeted Flask/Django upgrades and documented Python, Node and Rust migration adapters. Appropriate jobs exercise API replay, full data comparisons, schema constraints, requested additions, new writes, restarts and repeated migration. Database changes are explicit. A general repository job does not imply production data migration.

The older SuiteCRM adapter remains a bounded demonstration of the documented sales workflow. See [migration details](migrations.md) and adapter checks for exact requirements.

## Robotics

The trusted `goose-ros2` adapter provides pinned source replay, containerized ROS 2 build, independent algorithm checks and a Gazebo/Nav2 mission. Candidate code receives neither a Docker socket nor host API credentials or report paths. The baseline replays selected original algorithms with Python 2 division compatibility. It is not an original ROS 1 simulator run.

The first source is a pinned `rrt_exploration` revision. Other ROS projects require their own contracts and adapters. Nav2, Gazebo, SLAM and robot simulation infrastructure are reused. Hardware is not validated.

## Business operations

Inquiries link to intake. Proposals and delivery require customer acceptance. Operator authentication protects company actions. Customer tokens scope individual workspaces. AgentMail/custom email and Stripe Checkout with signed settlement are implemented. Missing keys leave real invoices unpaid; demonstrations use labelled local receipts.

The operator can authorize routine transactional notifications once. The worker then sends trusted lifecycle templates to linked customer addresses. Prospecting and arbitrary messages require exact-message authorization. Uncertain delivery does not silently retry.

Support uses the coordinator. Change requests become separately budgeted child engagements after fresh source upload. Maintenance checks delivered artifact integrity and prior verification. It does not monitor production, scan dependency registries, bill subscriptions or automatically deploy upgrades.

## Trust boundary

Uploads and execution use copies. Frozen evidence is hashed and inaccessible to candidate code. Verification checks both evidence and candidate changes. Tests exercise these failures, isolation and payment replay/mode/amount guards.

The agent knows public requirements and interfaces. Withheld expectations and independent checks do not prove absence of all untested behavior. This is an operator-run local prototype, without enterprise certification, a production multi-tenant isolation claim, high availability or automatic production rollback. Deployment and production cutover need a separate agreed operational plan.
